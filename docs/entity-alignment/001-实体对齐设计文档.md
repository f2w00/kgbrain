# Entity Alignment - 实体对齐服务

> 创建日期: 2026-06-08
> 最后更新: 2026-06-20
> 状态: 已实现（第二轮迭代）
> 作者: AI

## 1. 概述

实体对齐服务是数据 pipeline 的中间环节，用于将指定数据库表中指定字段的原始值自动映射到**持久化的标准化目标实体集合**，并将处理后的整行数据写入输出表。

与第一轮设计的关键区别：

| 维度 | 第一轮 | 第二轮 |
|------|--------|--------|
| 目标定义 | 请求时传入 `fields[].targets` 字符串数组 | 引用持久化的 `alignment_targets` 标准值集合 |
| 目标实体标识 | 纯字符串 | `target_set_id + label`，`label` 即标准输出值 |
| 未匹配行为 | `fallback_original`（保留原始值） | `needs_candidate`（进入候选集，等待人工审核），输出 null |
| 输出字段值 | 允许原始值作为兜底 | 只能是标准集标签或 null，不允许原始值 |
| 候选集 | 无 | 独立 `target_candidates` 表，审核后直接更新 target 或 mapping |
| 行级跟踪 | 只有 succeeded/failed | 新增 `waiting_target_review` 状态 |
| 候选召回 | 全量目标值进入 prompt | `pg_trgm` 模糊召回 topK 后进入 prompt |

典型场景：

```text
target_set_id: dynasty
targets: 唐, 宋, 元, 明, 清

source_table.dynasty 原始值: 唐朝 / 大唐 / 不详 / 辽 / 明清
输出字段值:          唐   / 唐   / null  / null / null

未匹配行（辽, 明清）→ processrecord status = waiting_target_review
                       → 录入 target_candidates（原始值层面）
                       → 人工审核后更新 target 或 mapping
                       → 下一轮对齐自动处理
```

## 2. 设计原则

1. **输出必须是标准化标签或 null**：原始值（raw_value）永远不能直接出现在输出字段中。无法匹配标准集的原始值输出 null，并通过等待审核流程进入候选集。
2. **标准值集合持久化**：目标实体集合不是请求参数，而是业务库中的 `alignment_targets` 记录。
3. **候选集驱动增量扩展**：对齐过程中发现的未匹配原始值自动进入候选集；人工审核后直接新增标准值或写入 mapping。
4. **整体处理状态跟踪**：通过 processrecord 模块按 `source_key` 记录每条源数据的整体处理状态，未对齐行标记为 `waiting_target_review`，等待下一轮对齐。
5. **去中心化存储**：服务 SQLite 存 job/资源元数据；业务 Postgres 存 targets、mapping、数据、处理记录。

## 3. 数据模型

### 3.1 标准值（Alignment Targets）

标准值表定义某个标准集下允许出现在最终 `output_table` 中的标签。

```text
alignment_targets 表（业务 Postgres）
─────────────────────────────────────────
target_set_id  TEXT NOT NULL              -- 标准集 ID，默认等于字段名
label          TEXT NOT NULL              -- 标准输出值，如 "唐"、"佛像"
created_at     TIMESTAMPTZ
updated_at     TIMESTAMPTZ
PRIMARY KEY (target_set_id, label)
```

`target_set_id` 是标准集命名空间。同一个标准集内 `label` 唯一，不同标准集可以有相同 `label`。

示例：

```text
target_set_id | label
--------------|------
dynasty       | 唐
dynasty       | 宋
category      | 佛像
category      | 瓷器
```

默认情况下，`target_set_id = fields.name`。如果不同字段需要复用同一标准集，字段配置可以显式传入 `target_set_id`。

实体对齐执行时会在业务 Postgres 中确保 `pg_trgm` 扩展和
`alignment_targets.label` 的 GIN trigram 索引存在：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX IF NOT EXISTS alignment_targets_label_trgm_idx
ON public.alignment_targets
USING gin (label gin_trgm_ops);
```

该索引用于从当前 `target_set_id` 的 label 中按字符相似度召回 topK 候选。

当前阶段不做以下内容：

- 不做 `target_sets` 表。
- 不做 `target_set_versions` 表。
- 不做 `target_items` 表。
- 不做 `target_id`。
- 不做 `aliases`。
- 不做发布流程。

别名关系由 `entity_alignment_mapping` 承担。例如 `唐朝 -> 唐`、`大唐 -> 唐` 都是 mapping 记录，不写入 target 表。

### 3.2 TargetCandidate（候选值）

对齐过程中发现的未匹配原始值会进入候选集，等待人工审核。候选集只作为审核队列，
不参与再次对齐时的运行时决策；再次对齐只参考 `alignment_targets` 和
`entity_alignment_mapping`。

```text
target_candidates 表（业务 Postgres）
─────────────────────────────────────────
id              TEXT PRIMARY KEY
target_set_id   TEXT NOT NULL             -- 对应 alignment_targets.target_set_id
raw_value       TEXT NOT NULL             -- 未匹配的原始值
frequency       INTEGER NOT NULL DEFAULT 1 -- 出现频次
status          TEXT NOT NULL DEFAULT 'pending'
                -- pending / resolved
resolution      TEXT                       -- add_as_label / map_to_existing / reject_as_null
resolved_label  TEXT                       -- add_as_label/map_to_existing 后的标准 label
review_reason   TEXT                       -- 人工备注或拒绝原因
created_at      TIMESTAMPTZ
updated_at      TIMESTAMPTZ
UNIQUE (target_set_id, raw_value)
```

候选集在目标集层面去重：同一个 `target_set_id + raw_value` 只产生一条候选记录。
重复出现时只累加 `frequency` 并更新 `updated_at`。

状态语义：

| 字段 | 值 | 说明 |
|------|----|------|
| `status` | `pending` | 待审核 |
| `status` | `resolved` | 已审核，结果已回写 target 或 mapping |
| `resolution` | `add_as_label` | 接受为新标准值 |
| `resolution` | `map_to_existing` | 映射到已有标准值 |
| `resolution` | `reject_as_null` | 确认为无意义值，后续输出 null |

审核完成后必须回写 `entity_alignment_mapping`。候选表只记录审核队列状态和审核结果摘要，
不会作为后续对齐的判断依据。

### 3.3 EntityAlignmentMapping（映射缓存）

与第一轮设计一致，按原始值存储最终映射结果。status 字段不再包含 `fallback_original`。

```text
entity_alignment_mapping 表（业务 Postgres）
─────────────────────────────────────────
id              BIGSERIAL PRIMARY KEY
target_set_id   TEXT NOT NULL      -- 关联的标准集 ID，默认等于 field_name
raw_value       TEXT NOT NULL
aligned_value   TEXT              -- matched 时为目标标签
status          TEXT NOT NULL     -- matched / unknown_to_null / needs_candidate
created_at      TIMESTAMPTZ
updated_at      TIMESTAMPTZ
last_used_at    TIMESTAMPTZ
use_count       BIGINT NOT NULL DEFAULT 1
CHECK (btrim(raw_value) <> ''),
CHECK (status IN ('matched', 'unknown_to_null', 'needs_candidate'))
UNIQUE (target_set_id, raw_value)
```

mapping 状态语义：

| status | aligned_value | 说明 |
|--------|---------------|------|
| `matched` | 目标标签 | 明确匹配到 `alignment_targets` 中的标准值 |
| `unknown_to_null` | null | 原始值为空、未知、无意义 |
| `needs_candidate` | null | 有实际含义但未匹配到任何目标实体，已进入 candidate 集 |

mapping 的复用边界是 `target_set_id + raw_value`。标准集是增量更新的当前态，不做版本，
因此 mapping 不再保存 `target_hash`、`targets_json` 或 `field_name`。

### 3.4 DataProcessRecords（整体处理状态）

记录每条源数据的整体处理状态，新增 `waiting_target_review` 状态。
`source_key` 是唯一身份；`process_type` 仅表示最近一次写入该状态的处理来源。

```text
data_process_records 表（业务 Postgres）
─────────────────────────────────────────
source_key   BIGINT PRIMARY KEY
process_type TEXT NOT NULL
status       TEXT NOT NULL     -- succeeded / failed / waiting_target_review
created_at   TIMESTAMPTZ
updated_at   TIMESTAMPTZ
```

当前不额外创建查询索引。`source_key` 主键已覆盖按行状态判断的查询；如果后续
需要批量查询失败或等待审核数据，再按实际查询补充 `status` 或
`process_type + status` 索引。

状态语义：

| status | 说明 |
|--------|------|
| `succeeded` | 该行所有字段都已完成对齐，且不存在 `needs_candidate` |
| `failed` | 处理过程中发生错误 |
| `waiting_target_review` | 该行存在未匹配到标准集的原始值，已进入候选集，等待目标集更新后重新对齐 |

### 3.5 Job 存储

与第一轮一致，存储在服务 SQLite 中。

```text
entity_alignment_jobs 表（服务 SQLite）
─────────────────────────────────────────
job_id              TEXT PRIMARY KEY
llm_resource_id     TEXT NOT NULL
database_resource_id TEXT NOT NULL
source_table        TEXT NOT NULL
output_table        TEXT NOT NULL
status              TEXT NOT NULL   -- pending / running / succeeded / failed
reuse_mapping       INTEGER NOT NULL -- 历史字段，当前固定复用 mapping
only_waiting_target_review INTEGER NOT NULL DEFAULT 0
key_field           TEXT NOT NULL
start_id            INTEGER
end_id              INTEGER
fuzzy_top_k         INTEGER NOT NULL DEFAULT 10
fields_json         TEXT NOT NULL DEFAULT '[]'
created_at          TEXT NOT NULL
started_at          TEXT
finished_at         TEXT
error_message       TEXT
```

说明：job 保存字段配置快照 `fields_json`，不单独保存顶层 `target_set_id`。
`fuzzy_top_k` 控制每个缺失 mapping 的 `raw_value` 召回多少个候选 label，默认 10。

## 4. 处理流程

### 4.1 标准对齐流程

```text
1. Connect RPC 接收 StartEntityAlignment 请求。
2. 校验 llm_resource_id、database_resource_id、source_table、output_table、key_field。
3. 对每个字段确定 target_set_id：未显式传入时使用字段名。
4. 创建 job 记录，返回 job_id。
5. 后台任务标记 job 为 running。
6. 从 ResourceService 配置存储读取 LLM 和 Database Resource。
7. 连接 database_resource_id 指向的业务 Postgres。
8. 确保 output_table 存在；不存在则按 source_table 普通列名和类型创建。
9. 确保 key_field 必填、非空、字段存在、值非 null，且不是待实体对齐字段。
10. 确保 output_table 在 key_field 上存在唯一约束或唯一索引。
11. 按 fields 顺序逐个字段准备 mapping。
12. 对当前字段从 source_table 指定 key_field 范围内取非 null、非空白的 distinct raw_value。
13. 从 alignment_targets 加载当前字段 target_set_id 下的 label 列表，并确认标准集非空。
14. 查 entity_alignment_mapping，固定复用已有结果。
15. 对未命中的 raw_value，先使用 pg_trgm 从 alignment_targets.label 召回 topK 候选。
16. LLM 只在召回的 topK 候选中做最终判定；召回为空时直接生成 needs_candidate。
17. LLM 校验规则：
    a. matched → aligned_value 必须属于本次召回的候选 label。
    b. unknown_to_null → aligned_value 为 null，原始值无意义。
    c. 无法匹配但有意义的原始值 → status = needs_candidate，aligned_value = null。
    d. 不再支持 fallback_original。
18. LLM 结果校验通过后按 batch_size 批量 upsert 到 entity_alignment_mapping。
19. 对所有 status=needs_candidate 的 mapping，upsert 到 target_candidates。
20. 所有字段 mapping 准备完成后，执行 output 写入：
    a. status=matched → 写入目标标签。
    b. status=unknown_to_null → 写入 null。
    c. status=needs_candidate → 写入 null（原始值不输出）。
21. 通过 processrecord 记录 source_key 的整体处理状态：
    a. 所有字段均 matched 或 unknown_to_null → succeeded。
    b. 存在 needs_candidate → waiting_target_review。
22. 成功则 job 标记 succeeded；失败则 job 标记 failed 并记录 error_message。
```

pg_trgm 召回 SQL 逻辑：

```sql
SELECT label
FROM public.alignment_targets
WHERE target_set_id = $1
  AND label % $2
ORDER BY similarity(label, $2) DESC, label ASC
LIMIT $3;
```

如果阈值召回结果不足 topK，会 fallback 到同一 `target_set_id` 下的全量
`similarity(label, raw_value)` 排序。

### 4.2 候选审核流程

```text
1. 人工或半自动查询 target_candidates（status=pending）。
2. 对每个候选值执行以下操作之一：
   a. "新增为标准值"（add_as_label）：向 alignment_targets 插入 label，并写 mapping。
   b. "映射到已有标准值"（map_to_existing）：target 表不变，写 mapping 到已有 label。
   c. "确认为无意义"（reject_as_null）：写 mapping 为 unknown_to_null。
3. 用户重新运行 StartEntityAlignment，自动处理上次 waiting_target_review 的行。
```

当前阶段不做 draft、publish 或 version。审核动作直接更新 target 或 mapping。

### 4.3 候选集去重规则

- 候选集在 target_set 级别去重：同一个 `target_set_id + raw_value` 不会重复录入。
- 频次累加：同一原始值在多次对齐中出现，frequency 递增，不产生重复候选。
- 已审核候选值再次出现时，不重新打开候选；运行时应命中已回写的 mapping。
- 当前不记录来源行明细；如后续审核需要上下文，再补充来源行表或样本字段。

### 4.4 重新对齐已标记行

```text
1. 用户启动新对齐任务。
2. 服务从 source_table 读取数据，但通过 processrecord 过滤：
   - 只处理 status=waiting_target_review 的行（或全量重新对齐）。
   - 已 succeeded 的行默认跳过，除非用户要求全量重跑。
3. 对 waiting_target_review 的行重新执行对齐流程。
4. 如果此次所有字段都成功匹配，行状态更新为 succeeded。
5. 如果仍有 needs_candidate，保持 waiting_target_review（或引用新候选 ID）。
```

## 5. 输入模型

### 5.1 StartEntityAlignment 请求

Connect RPC 请求示例：

```json
{
  "llm_resource_id": "qwen_local",
  "database_resource_id": "museum_pg",
  "source_table": "public.artifact_raw",
  "output_table": "public.artifact_aligned",
  "only_waiting_target_review": false,
  "key_field": "id",
  "start_id": 1000,
  "fuzzy_top_k": 10,
  "fields": [
    {
      "name": "dynasty",
      "batch_size": 20
    },
    {
      "name": "category",
      "target_set_id": "artifact_category",
      "batch_size": 20
    }
  ]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `llm_resource_id` | string | 是 | 用于读取 LLM Resource 配置 |
| `database_resource_id` | string | 是 | 用于读取 Database Resource 配置 |
| `source_table` | string | 是 | 原始数据表名 |
| `output_table` | string | 是 | 结果写入表名 |
| `only_waiting_target_review` | optional bool | 否 | 仅处理当前 `data_process_records.status = waiting_target_review` 的记录 |
| `key_field` | string | 是 | 输出写入幂等键字段 |
| `start_id` | optional int64 | 否 | 处理范围下界 |
| `end_id` | optional int64 | 否 | 处理范围上界 |
| `fuzzy_top_k` | optional int32 | 否 | 每个缺失 mapping 的 raw_value 召回候选 label 数量；默认 10 |
| `fields` | array | 是 | 待实体对齐的字段配置 |
| `fields.name` | string | 是 | 待处理字段名 |
| `fields.target_set_id` | optional string | 否 | 标准集 ID；未传时使用 `fields.name` |
| `fields.batch_size` | optional int32 | 否 | mapping/candidate 批量写入数据库的记录数；默认 20 |
| `fields.batch_concurrency` | optional int32 | 否 | 已禁用；当前服务端按单值串行调用 LLM，该字段会被忽略 |

与第一轮的关键变化：

- **移除了 `fields[].targets`**：目标来自 target_set，不再是请求参数。
- **增加了 `fields[].target_set_id` 可选字段**：默认使用字段名作为标准集 ID。
- **增加了 `only_waiting_target_review` 可选字段**：用于审核后仅重跑等待 target 审核的记录。
- **增加了 `fuzzy_top_k` 可选字段**：控制 pg_trgm 模糊召回候选数量。
- **移除了 `reuse_mapping` 开关**：实体对齐固定复用已有 mapping，LLM 只处理缺失 mapping 的原始值。

### 5.2 Target 与 Candidate 相关 RPC 接口

标准值只服务于 EntityAlignment，不单独拆 service，接口挂在 `EntityAlignmentService` 下。

其中 target 管理接口使用纯字符串标签数组：

- `ListAlignmentTargetsResponse.labels`
- `UpsertAlignmentTargetsRequest.labels`

```protobuf
service EntityAlignmentService {
  rpc ListAlignmentTargets(ListAlignmentTargetsRequest)
      returns (ListAlignmentTargetsResponse);

  rpc UpsertAlignmentTargets(UpsertAlignmentTargetsRequest)
      returns (UpsertAlignmentTargetsResponse);

  rpc DeleteAlignmentTarget(DeleteAlignmentTargetRequest)
      returns (DeleteAlignmentTargetResponse);

  rpc ListTargetCandidates(ListTargetCandidatesRequest)
      returns (ListTargetCandidatesResponse);

  rpc ReviewTargetCandidates(ReviewTargetCandidatesRequest)
      returns (ReviewTargetCandidatesResponse);
}
```

### 5.3 ReviewTargetCandidates 请求示例

```json
{
  "database_resource_id": "museum_pg",
  "source_table": "public.artifact_raw",
  "target_set_id": "dynasty",
  "actions": [
    {
      "candidate_id": "c1-...",
      "resolution": "add_as_label",
      "label": "辽"
    },
    {
      "candidate_id": "c2-...",
      "resolution": "map_to_existing",
      "label": "明"
    },
    {
      "candidate_id": "c3-...",
      "resolution": "reject_as_null",
      "review_reason": "无实际含义"
    }
  ]
}
```

审核即生效：`add_as_label` 会新增 target 并写 mapping，`map_to_existing` 只写 mapping。

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `database_resource_id` | string | 是 | 业务数据库资源 ID |
| `source_table` | string | 否 | 保留字段；当前 mapping 表固定写入 `public.entity_alignment_mapping`，该字段不影响写入位置 |
| `target_set_id` | string | 是 | 候选值所属标准集 ID |
| `actions` | array | 是 | 批量审核动作 |

注意：alignment 内部表按数据库资源共享，固定使用 `public.alignment_targets`、
`public.target_candidates` 和 `public.entity_alignment_mapping`。`source_table` 当前仅作为
保留字段，不参与 mapping 表路由。

`ListAlignmentTargets`、`UpsertAlignmentTargets`、`DeleteAlignmentTarget` 以及 candidate 相关
RPC 都需要显式传入 `database_resource_id`，因为标准值与候选值存储在业务数据库中。

## 6. 输出表规则

与第一轮基本一致，核心变化是输出字段值只能是标准标签或 null。

### 6.1 Upsert 幂等写入模式

规则：
- `key_field` 用于标识 `output_table` 中的一条结果记录。
- `key_field` 必须传入且不能为空。必须存在于 `source_table` 和 `output_table`。
- `key_field` 不能是任何待实体对齐字段。
- `source_table` 中 `key_field` 对应值不能为 null。
- `output_table` 必须在 `key_field` 上存在唯一约束或唯一索引。
- 写入时使用 `INSERT ... ON CONFLICT (key_field) DO UPDATE`。
- conflict update 时只更新本次请求 `fields.name` 对应字段。

### 6.2 输出字段值规则

```text
source 字段为 null        → 输出 null
source 字段 trim 后为空   → 输出 null
mapping status = matched  → 输出 aligned_value（目标标签）
mapping status = unknown_to_null → 输出 null
mapping status = needs_candidate → 输出 null
无 mapping 记录           → 输出 null（兜底）
```

不允许输出未匹配成功的原始值。

## 7. 映射规则

### 7.1 LLM 状态

| 状态 | aligned_value | 说明 |
|------|---------------|------|
| `matched` | 目标标签 | 明确匹配到目标集中的一个实体 |
| `unknown_to_null` | null | 原始值为空、未知、无意义 |
| `needs_candidate` | null | 有实际含义但不在当前目标集中，进入候选集 |

不再支持 `fallback_original`。

示例：

| raw_value | targets | status | aligned_value | 候选集 |
|-----------|---------|--------|---------------|--------|
| 唐朝 | 唐/宋/元/明/清 | matched | 唐 | - |
| 大唐 | 唐/宋/元/明/清 | matched | 唐 | - |
| 不详 | 唐/宋/元/明/清 | unknown_to_null | null | - |
| 辽 | 唐/宋/元/明/清 | needs_candidate | null | 辽 → 待审核 |
| 明清 | 明/清 | needs_candidate | null | 明清 → 待审核 |

### 7.2 Target 与 Mapping 的关系

`alignment_targets` 只定义最终允许输出的标准 `label`，不保存别名。原始值到标准值的关系由 mapping 表保存。

示例：

```text
alignment_targets:
target_set_id | label
dynasty       | 唐
dynasty       | 宋

entity_alignment_mapping:
target_set_id | raw_value | status  | aligned_value
dynasty       | 唐朝      | matched | 唐
dynasty       | 大唐      | matched | 唐
dynasty       | 不详      | unknown_to_null | null
dynasty       | 辽        | needs_candidate | null
```

因此当前阶段不需要 `aliases`。如果候选值被合并到已有标准值，只需要回写 mapping。

### 7.3 目标集标准化规则

```text
1. 根据字段 target_set_id 查询 alignment_targets。
2. 使用 label 构建目标实体列表。
3. 使用标准化后的 label 列表构造 LLM prompt。
```

## 8. 候选集审核流程

### 8.1 候选值来源

- 对齐过程中 LLM 判定为 `needs_candidate` 的原始值。
- 不存在于当前 target_set_id 下的 alignment_targets。
- LLM 判定为 `unknown_to_null` 的原始值不进入候选集。

### 8.2 审核操作

| 操作 | 含义 | 生效效果 |
|------|------|---------|
| `add_as_label` | 接受为新标准值 | 新增 `alignment_targets`，并写 mapping 到该 label |
| `map_to_existing` | 映射到已有标准值 | 不改 target 表，只写 mapping 到已有 label |
| `reject_as_null` | 确认为无意义 | 写 mapping 为 `unknown_to_null`，后续直接输出 null |

### 8.3 审核后生效

流程：
1. 用户在管理界面查询 pending 候选值。
2. 逐条或批量执行审核操作。
3. `add_as_label` 直接新增标准值，`map_to_existing` 直接回写 mapping。
4. 用户重新对齐 waiting_target_review 行。

推荐调用方式：审核完成后，重新调用 `StartEntityAlignment`，并传入：

- `source_table`：与原始任务完全一致
- `only_waiting_target_review = true`

当前阶段不做 draft、publish 和 target version。

再次对齐只参考 `alignment_targets` 和 `entity_alignment_mapping`。candidate 表只用于审核列表，
不会作为对齐时的判断依据。

## 9. 与 ProcessRecord 的集成

### 9.1 状态映射

| 对齐结果 | processrecord status |
|----------|---------------------|
| 所有字段 matched 或 unknown_to_null | `succeeded` |
| 存在 needs_candidate | `waiting_target_review` |
| 执行过程出错 | `failed` |

### 9.2 重新对齐语义

- 只重新处理 `waiting_target_review` 的行（或全量重新对齐）。
- 已 `succeeded` 的行默认跳过，除非用户要求全量重跑。
- 重新对齐后行状态重新计算。
- 使用 `waiting_target_review` 而非 `pending`，以区分还未处理的原始行。
- processrecord 只按 `source_key` 保存一条整体状态，不再按 `source_table` 或
  `process_type` 分别保存多条状态。

## 10. 枚举常量

```text
mapping status:     matched / unknown_to_null / needs_candidate
candidate status:   pending / resolved
candidate resolution: add_as_label / map_to_existing / reject_as_null
job status:         pending / running / succeeded / failed
record status:      succeeded / failed / waiting_target_review
```

## 11. 并发策略

与第一轮一致，保持不变。

- fields 默认按请求顺序串行处理。
- 每个 field 内缺失 mapping 的 raw values 逐个调用 LLM。
- `batch_size` 仅控制生成 mapping 后批量写入数据库的记录数。
- `batch_concurrency` 字段已禁用，服务端会忽略该字段。
- 所有单值调用 LLM 前必须获取 resource-level permit。
- 同一个 llm_resource_id 下所有 job 共享 resource 级并发限制。

## 12. 处理流程（完整版）

```text
1. 接收 StartEntityAlignment 请求，校验必填字段。
2. 对每个字段确定 target_set_id，未传时使用字段名。
3. 从 alignment_targets 加载 label 列表并构造单值 LLM prompt。
4. 创建 job 记录，标记 pending。
5. 后台标记 running，打开业务数据库连接。
6. 确保 output_table、entity_alignment_mapping 表存在。
7. 按 fields 逐个处理：
   a. 查询非空、非空白的 distinct raw_value。
   b. 加载已有 mapping 并固定复用。
   c. 计算缺失值。
   d. 逐个 raw_value 调用 LLM，校验结果。
   e. mapping 按 batch_size 批量写入 mapping 表。
   f. needs_candidate 写入 target_candidates。
8. 输出写入：
   a. SELECT FROM source LEFT JOIN mapping。
   b. matched → 目标标签，unknown_to_null → null，needs_candidate → null。
   c. ON CONFLICT DO UPDATE 分页写入。
9. 记录 processrecord：
   a. 检查每行是否仍存在 needs_candidate。
   b. 不存在 needs_candidate → succeeded，否则 → waiting_target_review。
10. 标记 job succeeded / failed。
```
