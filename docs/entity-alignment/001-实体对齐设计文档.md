# Entity Alignment - 实体对齐服务

> 创建日期: 2026-06-08
> 状态: 设计阶段
> 作者: AI

## 1. 概述

实体对齐服务是数据 pipeline 的中间环节，用于将指定数据库表中指定字段的原始值自动映射到调用者给定的目标实体列表，并将处理后的整行数据写入输出表。

典型场景:

```text
source_table.dynasty 原始值: 唐朝 / 大唐 / 不详 / 辽 / 明清
targets: ["唐", "宋", "元", "明", "清"]
输出字段值: 唐 / 唐 / null / 辽 / 明清
```

该服务不做人工确认，不返回预览结果，直接作为 pipeline 的自动处理步骤执行。

## 2. 设计边界

当前版本只处理以下范围:

- 从一个 `source_table` 读取数据。
- 将处理结果插入一个调用者指定的 `output_table`。
- 通过 `llm_resource_id` 选择 LLM 配置。
- 通过 `database_resource_id` 选择数据库连接配置。
- 一次请求可传入多个字段，但服务内部按字段逐个处理。
- 每个字段使用调用者传入的简单字符串目标列表，例如 `["唐", "宋"]`。
- 只对字段的 distinct 原始值调用 LLM，不按数据行逐行调用 LLM。
- distinct 原始值按批次调用 LLM，字段级 `batch_size` 可选，不传时系统默认 `50`。
- mapping 结果持久化到 Postgres，并支持复用。
- 不处理输出表去重、批次隔离、人工审核、下游消费策略。

## 3. 输入模型

Connect RPC 请求示例:

```json
{
  "llm_resource_id": "qwen_local",
  "database_resource_id": "museum_pg",
  "source_table": "public.artifact_raw",
  "output_table": "public.artifact_aligned",
  "reuse_mapping": true,
  "fields": [
    {
      "name": "dynasty",
      "targets": ["唐", "宋", "元", "明", "清"]
    },
    {
      "name": "category",
      "targets": ["瓷器", "书画", "青铜器"],
      "batch_size": 100
    }
  ]
}
```

字段说明:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `llm_resource_id` | string | 是 | 用于读取 LLM Resource 配置 |
| `database_resource_id` | string | 是 | 用于读取 Database Resource 配置 |
| `source_table` | string | 是 | 原始数据表名，属于 `database_resource_id` 指向的数据库 |
| `output_table` | string | 是 | 结果写入表名，属于 `database_resource_id` 指向的数据库，由调用者指定 |
| `reuse_mapping` | optional bool | 否 | 是否复用已有 mapping；未传时按 true 处理 |
| `fields` | array | 是 | 待实体对齐的字段配置 |
| `fields.name` | string | 是 | 待处理字段名 |
| `fields.targets` | string[] | 是 | 目标实体列表 |
| `fields.batch_size` | optional int32 | 否 | 当前字段 LLM 批处理大小；未传时默认 50 |

## 4. 输出表规则

`output_table` 是 pipeline 的结果表，位于 `database_resource_id` 指向的数据库中。

规则:

- 如果 `output_table` 不存在，创建一张与 `source_table` 字段结构一致的表。
- 如果 `output_table` 已存在，直接继续插入处理后的数据。
- 不清空、不覆盖、不删除旧数据。
- 不额外添加 `job_id` 字段。
- 不区分批次。
- 未配置处理的字段原样复制。
- 配置处理的字段写入对齐后的值。

示例:

```text
source_table: public.artifact_raw
字段: id | name | dynasty | category

output_table: public.artifact_aligned
字段: id | name | dynasty | category
```

如果处理字段为 `dynasty`，则 `dynasty` 写入对齐后的值，其他字段保持原值。

重复插入、清空输出表、按批次隔离等策略由调用方或后续 pipeline 阶段自行处理，当前服务不负责。

## 5. 映射规则

每个原始字段值映射为以下三种状态之一:

| 状态 | 写入值 | 说明 |
|------|--------|------|
| `matched` | targets 中的某个值 | 明确匹配到目标实体 |
| `unknown_to_null` | `null` | 原始值为空、未知、无意义 |
| `fallback_original` | 原始值 | 未匹配成功，但原始值有实际含义 |

示例:

| raw_value | targets | aligned_value | status |
|-----------|---------|---------------|--------|
| 唐朝 | `["唐", "宋"]` | 唐 | matched |
| 大唐 | `["唐", "宋"]` | 唐 | matched |
| 不详 | `["唐", "宋"]` | null | unknown_to_null |
| 辽 | `["唐", "宋"]` | 辽 | fallback_original |
| 明清 | `["明", "清"]` | 明清 | fallback_original |

## 6. Mapping 存储

mapping 存储在 `database_resource_id` 指向的业务 Postgres 中，不存储在服务本地 SQLite。

mapping 不使用大 JSON 存储，而是按 raw value 一行存储，便于复用、增量写入、索引、排查和批量更新。

推荐表名:

```text
entity_alignment_mapping
```

推荐字段:

```text
id
field_name
target_hash
targets_json
raw_value
aligned_value
status
created_at
updated_at
last_used_at
use_count
```

唯一约束:

```text
(field_name, target_hash, raw_value)
```

`target_hash` 由标准化后的 targets 计算得到。目标列表不同，同一个 raw value 的映射结果可能不同，因此复用维度不能只使用 `field_name + raw_value`。

示例:

```text
raw_value = 辽
targets = ["唐", "宋", "元", "明", "清"] -> fallback_original: 辽
targets = ["唐", "宋", "辽", "金"] -> matched: 辽
```

## 7. Job 存储

job 记录存储在服务自己的 SQLite 中，用于记录异步任务状态。

推荐表名:

```text
entity_alignment_jobs
```

推荐字段:

```text
job_id
llm_resource_id
database_resource_id
source_table
output_table
status
reuse_mapping
created_at
started_at
finished_at
error_message
```

状态:

```text
pending
running
succeeded
failed
```

job 只用于任务状态记录，不写入 `output_table`，也不用于区分输出批次。

存储分布:

```text
服务 SQLite:
- entity_alignment_jobs
- llm_resources
- database_resources

业务 Postgres:
- source_table
- output_table
- entity_alignment_mapping
```

## 8. 处理流程

```text
1. Connect RPC 接收 StartEntityAlignment 请求。
2. 校验 llm_resource_id、database_resource_id、source_table、output_table、fields。
3. 创建 job 记录，返回 job_id。
4. 后台任务标记 job 为 running。
5. 从 ResourceService 配置存储读取 LLM 和 Database Resource。
6. 连接 database_resource_id 指向的业务 Postgres。
7. 确保 output_table 存在；不存在则按 source_table 字段结构创建。
8. 按 fields 顺序逐个字段处理。
9. 对当前字段从 source_table 取 distinct raw_value。
10. 计算当前 targets 的 target_hash。
11. reuse_mapping=true 时查 entity_alignment_mapping 复用已有结果。
12. 未命中的 raw_value 按 batch_size 分批调用 LLM。
13. 每批 LLM 结果 upsert 到 entity_alignment_mapping。
14. 所有字段 mapping 准备完成后，读取 source_table 数据。
15. 根据 mapping 转换配置字段。
16. 将转换后的整行数据 insert 到 output_table。
17. 成功则 job 标记 succeeded；失败则 job 标记 failed 并记录 error_message。
```

## 9. Connect RPC 接口

当前阶段只定义 proto，不实现 Go 代码。

服务:

```text
EntityAlignmentService
```

RPC:

```text
StartEntityAlignment: 启动异步实体对齐任务
GetEntityAlignmentJob: 查询任务状态
```

不设计同步执行 RPC，因为该任务可能涉及百万级数据、LLM 分批调用和数据库批量写入，同步等待容易触发超时且不利于失败恢复。
