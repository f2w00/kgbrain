# Entity Alignment - 实体对齐服务

> 创建日期: 2026-06-08
> 状态: 设计阶段
> 作者: AI

## 1. 概述

实体对齐服务是数据 pipeline 的中间环节，用于将指定数据库表中指定字段的原始值自动映射到调用者给定的目标实体列表，并将处理后的整行数据写入输出表。

典型场景:

```text
source_table.dynasty 原始值: 唐朝 / 大唐 / 不详 / 辽 / 明清
targets: ["唐", "宋", "元", "明", "清"]
输出字段值: 唐 / 唐 / null / 辽 / 明清
```

该服务不做人工确认，不返回预览结果，直接作为 pipeline 的自动处理步骤执行。

## 2. 设计边界

当前版本只处理以下范围:

- 从一个 `source_table` 读取数据。
- `source_table` 是上游 pipeline 已经标准化处理过的输入表。
- 将处理结果插入一个调用者指定的 `output_table`。
- 通过 `llm_resource_id` 选择 LLM 配置。
- 通过 `database_resource_id` 选择数据库连接配置。
- 一次请求可传入多个字段，但服务内部按字段逐个处理。
- 每个字段使用调用者传入的简单字符串目标列表，例如 `["唐", "宋"]`。
- 只对字段的 distinct 原始值调用 LLM，不按数据行逐行调用 LLM。
- distinct 原始值按批次调用 LLM，字段级 `batch_size` 可选，不传时系统默认 `20`。
- 同一个字段内的多个 LLM batch 可以并发调用，字段级 `batch_concurrency` 可选。
- 同一个 `llm_resource_id` 下所有 job 共享 resource 级 LLM 并发限制。
- mapping 结果持久化到 Postgres，并支持复用。
- mapping 跨表复用，只要 `field_name`、`target_hash` 和 `raw_value` 一致即可复用。
- `targets` 会经过 trim、去空、去重、排序后计算 `target_hash`。
- `key_field` 必填且不能为空，服务统一使用 upsert 写入。
- 不完整 mapping 不持久化；只有完整且校验通过的 mapping 才写入 Postgres。
- 不处理人工审核、下游消费策略、任务取消、暂停、恢复和进度百分比统计。

## 3. 输入模型

Connect RPC 请求示例:

```json
{
  "llm_resource_id": "qwen_local",
  "database_resource_id": "museum_pg",
  "source_table": "public.artifact_raw",
  "output_table": "public.artifact_aligned",
  "reuse_mapping": true,
  "key_field": "id",
  "start_id": 1000,
  "fields": [
    {
      "name": "dynasty",
      "targets": ["唐", "宋", "元", "明", "清"]
    },
    {
      "name": "category",
      "targets": ["瓷器", "书画", "青铜器"],
      "batch_size": 20,
      "batch_concurrency": 1
    }
  ]
}
```

字段说明:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `llm_resource_id` | string | 是 | 用于读取 LLM Resource 配置 |
| `database_resource_id` | string | 是 | 用于读取 Database Resource 配置 |
| `source_table` | string | 是 | 原始数据表名，属于 `database_resource_id` 指向的数据库 |
| `output_table` | string | 是 | 结果写入表名，属于 `database_resource_id` 指向的数据库，由调用者指定 |
| `reuse_mapping` | optional bool | 否 | 是否复用已有 mapping；未传时按 true 处理 |
| `key_field` | string | 是 | 输出写入幂等键字段；必须传入且不能为空 |
| `start_id` | optional int64 | 否 | 处理范围下界，基于 `key_field` 过滤；未传表示无下界 |
| `end_id` | optional int64 | 否 | 处理范围上界，基于 `key_field` 过滤；未传表示无上界，即一直处理到最后 |
| `fields` | array | 是 | 待实体对齐的字段配置 |
| `fields.name` | string | 是 | 待处理字段名 |
| `fields.targets` | string[] | 是 | 目标实体列表 |
| `fields.batch_size` | optional int32 | 否 | 当前字段 LLM 批处理大小；未传时默认 20 |
| `fields.batch_concurrency` | optional int32 | 否 | 当前字段 LLM batch 并发数；未传时使用系统默认值 |

## 4. 输出表规则

`output_table` 是 pipeline 的结果表，位于 `database_resource_id` 指向的数据库中。

规则:

- 如果 `output_table` 不存在，创建一张与 `source_table` 普通列名和类型一致的表。
- 自动创建 `output_table` 时，不复制主键、唯一约束、索引、外键、默认值和触发器。
- 自动创建 `output_table` 后，服务会基于 `key_field` 创建唯一索引。
- 服务不会把 `key_field` 创建为 `PRIMARY KEY`。
- 如果 `output_table` 已存在，校验表结构兼容后继续写入。
- 如果 `output_table` 已存在，服务只校验 `key_field` 上存在唯一约束或唯一索引，不自动修改已有表结构。
- 不清空、不删除旧数据。
- 不额外添加 `job_id` 字段。
- 不区分批次。
- 未配置处理的字段原样复制。
- 配置处理的字段写入对齐后的值。
- `output_table` 统一使用 upsert 幂等写入。

示例:

```text
source_table: public.artifact_raw
字段: id | name | dynasty | category

output_table: public.artifact_aligned
字段: id | name | dynasty | category
```

如果处理字段为 `dynasty`，则 `dynasty` 写入对齐后的值，其他字段保持原值。

### 4.1 Upsert 幂等写入模式

当前版本只支持 upsert 幂等写入模式，不支持追加写入模式。

规则:

- `key_field` 用于标识 `output_table` 中的一条结果记录。
- `key_field` 必须传入且不能为空。
- `key_field` 必须存在于 `source_table` 和 `output_table`。
- `key_field` 不能是任何待实体对齐字段。
- `source_table` 中 `key_field` 对应值不能为 null。
- `output_table` 必须在 `key_field` 上存在唯一约束或唯一索引。
- 如果 `output_table` 不存在，服务创建表后为 `key_field` 创建唯一索引。
- 服务不会把 `key_field` 创建为 `PRIMARY KEY`。
- 如果 `output_table` 已存在，服务只校验唯一约束或唯一索引，不自动修改已有表结构。
- 写入时使用 `INSERT ... ON CONFLICT (key_field) DO UPDATE`。
- insert 时写入完整行，未配置处理的字段写入 `source_table` 原值。
- conflict update 时只更新本次请求 `fields.name` 对应字段。
- conflict update 时不更新 `key_field`，也不更新本次未配置处理的字段。

该模式下，同一 source row 重复处理不会产生重复输出，而会刷新本次请求声明的对齐字段。
如果 `source_table` 的未处理字段发生变化，单独重跑某个对齐字段不会同步这些未处理字段。

## 5. 映射规则

每个原始字段值映射为以下三种状态之一:

| 状态 | 写入值 | 说明 |
|------|--------|------|
| `matched` | targets 中的某个值 | 明确匹配到目标实体 |
| `unknown_to_null` | `null` | 原始值为空、未知、无意义 |
| `fallback_original` | 原始值 | 未匹配成功，但原始值有实际含义 |

示例:

| raw_value | targets | aligned_value | status |
|-----------|---------|---------------|--------|
| 唐朝 | `["唐", "宋"]` | 唐 | matched |
| 大唐 | `["唐", "宋"]` | 唐 | matched |
| 不详 | `["唐", "宋"]` | null | unknown_to_null |
| 辽 | `["唐", "宋"]` | 辽 | fallback_original |
| 明清 | `["明", "清"]` | 明清 | fallback_original |

补充规则:

- `matched` 的 `aligned_value` 必须属于标准化后的 `targets`。
- `unknown_to_null` 的 `aligned_value` 必须为 null。
- `fallback_original` 允许输出不在 `targets` 内的原始有效值。
- `fallback_original` 写入时使用当前 source row 的原始值，不使用 mapping 表中的 `raw_value` 覆盖。
- 原始值同时指向多个目标实体时，不强行选择单个 target，按 `fallback_original` 处理。
- 原始值为 null 时直接输出 null，不进入 mapping。
- 原始值 trim 后为空字符串时直接输出 null，不进入 mapping。
- 其他原始值原样进入 mapping，不执行 trim、大小写归一、全半角转换或其他归一化处理。

`targets` 标准化规则:

```text
1. 对每个 target 执行 trim。
2. 移除空字符串。
3. 去重。
4. 排序。
5. 使用排序后的 targets 计算 target_hash。
6. targets_json 存储同一份标准化后的 targets。
```

`raw_value` 处理规则:

```text
1. null 不进入 mapping，直接输出 null。
2. trim 后为空字符串不进入 mapping，直接输出 null。
3. 其他 raw_value 原样存储和复用。
4. 当前版本不对 raw_value 做归一化处理。
```

## 6. Mapping 存储

mapping 存储在 `database_resource_id` 指向的业务 Postgres 中，不存储在服务本地 SQLite。

mapping 不使用大 JSON 存储，而是按 raw value 一行存储，便于复用、增量写入、索引、排查和批量更新。

推荐表名:

```text
entity_alignment_mapping
```

推荐字段:

```text
id
field_name
target_hash
targets_json
raw_value
aligned_value
status
created_at
updated_at
last_used_at
use_count
```

唯一约束:

```text
(field_name, target_hash, raw_value)
```

`target_hash` 由标准化后的 targets 计算得到。目标列表不同，同一个 raw value 的映射结果可能不同，因此复用维度不能只使用 `field_name + raw_value`。

mapping 跨表复用。只要 `field_name`、`target_hash` 和 `raw_value` 一致，不同 `source_table` 中的同名字段可以复用同一条 mapping。

`raw_value` 保存 source 字段原始值，用于唯一约束、复用查找和排查。

`raw_value` 不允许为 null。source 字段为 null 或 trim 后为空字符串时，服务直接输出 null，不写入 mapping。

建议约束:

```text
raw_value IS NOT NULL
btrim(raw_value) <> ''
status IN ('matched', 'unknown_to_null', 'fallback_original')
```

mapping 表只保存最终可复用结果，不保存 `pending`、`running`、`failed` 或 `partial` 等中间状态。

`reuse_mapping` 语义:

- `reuse_mapping=true` 时，先查询已有 mapping，只对未命中的 raw value 调用 LLM。
- `reuse_mapping=true` 时，并发 upsert 冲突建议保留已有 mapping。
- `reuse_mapping=false` 时，不复用已有 mapping，所有 distinct raw value 都重新调用 LLM。
- `reuse_mapping=false` 时，upsert 覆盖已有 mapping。

示例:

```text
raw_value = 辽
targets = ["唐", "宋", "元", "明", "清"] -> fallback_original: 辽
targets = ["唐", "宋", "辽", "金"] -> matched: 辽
```

## 7. 数据库侧写入与 Mapping Join

output 写入阶段优先采用数据库侧批量写入方案:

```text
INSERT INTO output_table (...)
SELECT ...
FROM source_table
LEFT JOIN entity_alignment_mapping ...
ON CONFLICT (key_field) DO UPDATE ...
```

mapping join 使用原始 `raw_value`，不使用归一化值。

以字段 `dynasty` 为例:

```sql
LEFT JOIN entity_alignment_mapping m_dynasty
  ON m_dynasty.field_name = 'dynasty'
 AND m_dynasty.target_hash = '<dynasty_target_hash>'
 AND m_dynasty.raw_value = s."dynasty"::text
```

字段输出表达式示例:

```sql
CASE
  WHEN s."dynasty" IS NULL THEN NULL
  WHEN btrim(s."dynasty"::text) = '' THEN NULL
  WHEN m_dynasty.raw_value IS NOT NULL THEN
    CASE m_dynasty.status
      WHEN 'matched' THEN m_dynasty.aligned_value
      WHEN 'unknown_to_null' THEN NULL
      WHEN 'fallback_original' THEN s."dynasty"
      ELSE s."dynasty"
    END
  ELSE s."dynasty"
END AS "dynasty"
```

完整 upsert 示例:

```sql
INSERT INTO "public"."artifact_aligned" ("id", "name", "dynasty", "category")
SELECT
  s."id",
  s."name",
  CASE
    WHEN s."dynasty" IS NULL THEN NULL
    WHEN btrim(s."dynasty"::text) = '' THEN NULL
    WHEN m_dynasty.raw_value IS NOT NULL THEN
      CASE m_dynasty.status
        WHEN 'matched' THEN m_dynasty.aligned_value
        WHEN 'unknown_to_null' THEN NULL
        WHEN 'fallback_original' THEN s."dynasty"
        ELSE s."dynasty"
      END
    ELSE s."dynasty"
  END AS "dynasty",
  CASE
    WHEN s."category" IS NULL THEN NULL
    WHEN btrim(s."category"::text) = '' THEN NULL
    WHEN m_category.raw_value IS NOT NULL THEN
      CASE m_category.status
        WHEN 'matched' THEN m_category.aligned_value
        WHEN 'unknown_to_null' THEN NULL
        WHEN 'fallback_original' THEN s."category"
        ELSE s."category"
      END
    ELSE s."category"
  END AS "category"
FROM "public"."artifact_raw" s
LEFT JOIN "public"."entity_alignment_mapping" m_dynasty
  ON m_dynasty.field_name = 'dynasty'
 AND m_dynasty.target_hash = '<dynasty_target_hash>'
 AND m_dynasty.raw_value = s."dynasty"::text
LEFT JOIN "public"."entity_alignment_mapping" m_category
  ON m_category.field_name = 'category'
 AND m_category.target_hash = '<category_target_hash>'
 AND m_category.raw_value = s."category"::text
ON CONFLICT ("id") DO UPDATE
SET
  "dynasty" = EXCLUDED."dynasty",
  "category" = EXCLUDED."category";
```

规则:

- source 字段为 null 时直接输出 null。
- source 字段 trim 后为空字符串时直接输出 null。
- 其他值按原始值 join mapping。
- `fallback_original` 输出当前 source row 原值。
- 理论上所有非 null、非空 raw value 都应有 mapping。
- 如果 join 不上 mapping，兜底输出 source 原值。
- 待处理字段当前只支持 text、varchar、char 等文本兼容类型。
- `ON CONFLICT DO UPDATE` 只更新本次请求 `fields.name` 对应字段。
- `ON CONFLICT DO UPDATE` 不更新 `key_field`，也不更新本次未配置处理的字段。

## 8. Job 存储

job 记录存储在服务自己的 SQLite 中，用于记录异步任务状态。

推荐表名:

```text
entity_alignment_jobs
```

推荐字段:

```text
job_id
llm_resource_id
database_resource_id
source_table
output_table
status
reuse_mapping
key_field
start_id
end_id
created_at
started_at
finished_at
error_message
```

状态:

```text
pending
running
succeeded
failed
```

job 只用于任务状态记录，不写入 `output_table`，也不用于区分输出批次。

`key_field` 保存请求中的幂等写入键字段，用于排查 job 写入模式和失败原因。

`start_id` 和 `end_id` 保存本次任务的处理范围，用于排查任务只处理了哪一段
`key_field` 数据。

存储分布:

```text
服务 SQLite:
- entity_alignment_jobs
- llm_resources
- database_resources

业务 Postgres:
- source_table
- output_table
- entity_alignment_mapping
```

## 9. 处理流程

```text
1. Connect RPC 接收 StartEntityAlignment 请求。
2. 校验 llm_resource_id、database_resource_id、source_table、output_table、fields、key_field。
3. 创建 job 记录，返回 job_id。
4. 后台任务标记 job 为 running。
5. 从 ResourceService 配置存储读取 LLM 和 Database Resource。
6. 连接 database_resource_id 指向的业务 Postgres。
7. 确保 output_table 存在；不存在则按 source_table 普通列名和类型创建。
8. 确保 key_field 必填、非空、字段存在、值非 null，且不是待实体对齐字段。
9. 确保 output_table 在 key_field 上存在唯一约束或唯一索引。
10. 按 fields 顺序逐个字段准备 mapping。
11. 对当前字段从 source_table 指定 `key_field` 范围内取非 null、非空白的 distinct raw_value。
12. 标准化当前 targets 并计算 target_hash。
13. reuse_mapping=true 时查 entity_alignment_mapping 复用已有结果。
14. 未命中的 raw_value 按 batch_size 分批调用 LLM。
15. 每批 LLM 结果完整校验通过后 upsert 到 entity_alignment_mapping。
16. 所有字段 mapping 准备完成后，读取 source_table 指定 `key_field` 范围内的数据。
17. 根据 mapping 同时转换所有配置字段。
18. 将指定范围内转换后的整行数据 upsert 到 output_table。
19. 成功则 job 标记 succeeded；失败则 job 标记 failed 并记录 error_message。
```

## 10. 多字段处理语义

一次请求可以包含多个 `fields`。服务内部按 `fields` 顺序逐个准备 mapping，但不会在单个字段完成后立即写入 `output_table`。

处理规则:

- 每个字段独立计算 `target_hash`。
- 每个字段独立查询非 null、非空白的 distinct `raw_value`。
- 每个字段独立复用或生成 mapping。
- 所有字段 mapping 都准备完成后，服务才读取 `source_table` 并执行一次 `output_table` 写入。
- `output_table` 写入时同时应用所有 `fields` 的 mapping。
- upsert 冲突时只更新本次请求 `fields.name` 对应字段。
- 如果任一字段 mapping 准备失败，job failed，且不写 `output_table`。
- 已写入 `entity_alignment_mapping` 的 mapping 不回滚，可供后续任务复用。

不采用以下流程:

```text
1. 处理字段 A mapping。
2. 字段 A 完成后立即写入或 upsert output_table。
3. 处理字段 B mapping。
4. 字段 B 完成后再次写入或 upsert output_table。
```

这样可以避免某个字段成功、另一个字段失败时产生半成品 output，也可以避免不同字段任务互相覆盖已经对齐的字段。

## 11. Mapping 中间状态

当前版本不持久化不完整 mapping。

状态分布:

```text
服务内存:
- 当前正在处理的 field
- 当前 field 的 missing raw_values
- 当前 batch
- LLM 返回的临时结果
- 待 upsert 的 batch mapping

服务 SQLite:
- job 级状态
- job 错误信息

业务 Postgres:
- source_table
- output_table
- 已完成、可复用的最终 mapping
```

写入规则:

- LLM batch 返回完整且通过校验后，整批 mapping upsert 到 Postgres。
- LLM batch 返回失败、缺失、重复或非法值时，该 batch 不写 mapping。
- batch 失败后可按重试策略重试；最终失败则 job failed。
- 服务崩溃时，未写入 Postgres 的 batch 结果丢弃。
- job 重跑时重新查询 mapping，只处理仍然 missing 的 raw value。

LLM batch 校验规则:

- 返回结果必须覆盖 batch 中全部 `raw_value`。
- 返回结果不能包含 batch 外的 `raw_value`。
- 返回结果不能重复。
- `matched` 的 `aligned_value` 必须属于标准化后的 `targets`。
- `unknown_to_null` 的 `aligned_value` 必须为 null。
- `fallback_original` 的 `aligned_value` 不作为最终写入依据，最终写入使用当前 source row 原值。
- 任一结果非法时，整个 batch 视为失败，不写部分 mapping。

output 写入失败语义:

- 只有所有字段 mapping 都准备完成后才进入 output 写入阶段。
- output 写入阶段应尽量在单个数据库事务内完成。
- output 写入失败时，job failed，事务回滚本次 output 写入。
- mapping 写入不包含在 output 写入事务内，job 失败后已生成 mapping 继续保留。

mapping 表只存以下最终状态:

```text
matched
unknown_to_null
fallback_original
```

不存以下中间状态:

```text
pending
running
failed
partial
```

## 12. 并发策略

当前版本不使用 Redis。

一个 job 内:

- `fields` 默认按请求顺序串行处理。
- 每个 field 内 raw values 按 `batch_size` 分批。
- 同一个 field 内 batch 可以并发调用 LLM。
- `batch_concurrency` 未传时使用系统默认值。
- `batch_concurrency` 必须大于 0。
- 实际 batch 并发数不能超过系统配置的 `max_batch_concurrency`。
- 所有 batch 调用 LLM 前必须获取 `llm_resource_id` 对应的 resource-level permit。
- 同一个 `llm_resource_id` 下所有 job 共享 resource 级并发限制。
- permit 数量来自 LLM Resource 的 `max_concurrency`；未配置时使用系统默认值。
- 所有 batch 的完整合法结果会立即 upsert 到 Postgres。
- 任一 batch 最终失败时，当前 field 失败，job failed，不进入 output 写入阶段。

多个 job 之间:

- 允许并发准备 mapping。
- 并发 job 可能对同一 missing raw value 重复调用 LLM。
- `entity_alignment_mapping` 通过唯一约束保证最终只有一条 mapping。
- `reuse_mapping=true` 时，并发冲突建议保留已有 mapping。
- `reuse_mapping=false` 时，允许覆盖已有 mapping。
- 相同 `output_table`、相同 `key_field`、相同处理字段并发执行时，后提交的 job 覆盖该字段。
- 当前版本不做字段级任务锁。

## 13. 并发与批处理默认配置

当前默认值面向 4B 模型和 4096 context window，优先保证结构化输出稳定性。

系统默认配置:

```text
default_batch_size = 20
max_batch_size = 50
default_batch_concurrency = 1
max_batch_concurrency = 2
default_llm_resource_concurrency = 1
max_llm_resource_concurrency = 2
```

实际生效值:

```text
effective_batch_size = min(
  request.fields.batch_size or system.default_batch_size,
  system.max_batch_size
)

effective_batch_concurrency = min(
  request.fields.batch_concurrency or system.default_batch_concurrency,
  system.max_batch_concurrency
)

resource_concurrency = min(
  llm_resource.max_concurrency or system.default_llm_resource_concurrency,
  system.max_llm_resource_concurrency
)
```

`effective_batch_concurrency` 控制单个 field 内最多启动多少个 batch worker。
真正的全局 LLM 调用数由 `llm_resource_id` 对应的 resource-level semaphore 控制。

即使多个 job 或多个 field 的 batch worker 同时运行，同一个 `llm_resource_id` 下的 LLM 调用数也不能超过 `resource_concurrency`。

## 14. Connect RPC 接口

当前阶段只定义 proto，不实现 Go 代码。

服务:

```text
EntityAlignmentService
```

RPC:

```text
StartEntityAlignment: 启动异步实体对齐任务
GetEntityAlignmentJob: 查询任务状态
```

不设计同步执行 RPC，因为该任务可能涉及百万级数据、LLM 分批调用和数据库批量写入，同步等待容易触发超时且不利于失败恢复。
